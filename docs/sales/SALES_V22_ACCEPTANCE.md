## 实施结果与数据关系

- **A 数据**：Case 包含 patientName、doctorId、hospitalId、department、summary。同一 Case 可关联多个 Order；患者姓名仅在获授权表单/详情显示，不加入首页、列表和通知。新建病例自动选中；旧病例缺失姓名允许补齐，已有身份不得通过订单覆盖。
- **B 四步表单**：客户与病例 → 服务需求 → 资料上传 → 确认并提交。clinicalRequirements 与 designRequirements 分别保存；兼容旧 requirements。服务项目与 plannedStages 分离；阶段按三维重建、CAD设计、有限元分析、3D打印排序。数量正整数、预计交付日晚于今日，浏览器和本地服务共用校验。缺少已审核上游成果时禁止仅选下游提交。
- **C 列表**：有 Label 的即时 AND 筛选、关键词防抖、重置回第一页；普通销售无历史访问申请入口，模型与本地服务也拒绝该权限。默认每页12条、官方分页。提交后清理原筛选、定位第一条，3.5秒一次性强调，尊重 reduced-motion。
- **D 详情**：四张纵向 Card：订单概览、专业进度、资料附件、操作记录，无 Tabs。3列信息，状态仅一次，专业进度复用工程师原阶段卡片结构。未分配的旧进行中记录不伪装有负责人，展示待分配；新受理阶段分配明确的隔离设计团队后进入进行中。
- **E 首页**：近期最多6条、原工程师图标/表格结构、无新建按钮。日期限定账号授权3/6月范围；查看全部保留相同范围。修复旧路由缓存覆盖新范围的问题。
- **F 回归**：实际操作销售流程、双账号、陈屿项目列表/详情、CAD、三维重建只读成果、多标签，检查三种桌面宽度与两主题。

关系为 `Case.id → Order.caseId`；`Order.id → Project.orderId`；`Order.projectId → Project.id`；`Project.taskIds → Order.stages[].taskId`。当前受理产生稳定 `SP-订单ID`，source 为 `isolated-sales`，界面明确标示独立演示项目。未生成或伪装真实工程师项目编号，不提供无效专业编辑链接，不伪造成果文件。

## 尚未真实打通的接口

1. 销售订单→正式工程项目→专业任务的服务端创建、指派、结果同步；目前是本地隔离SP模型，不映射到陈屿真实任务。
2. 正式订单数据库、审计存储、主管授权和医院权限服务；浏览器按账号隔离仅用于原型，不替代服务端生产鉴权。本地order-validate检查登录角色、锁屏、账号一致性和字段日期，不是正式订单落库。
3. 影像云导入、DICOM序列解析、NIfTI医学校验、大文件分片；本地真实Blob每文件20MB，文件可读取不等于医疗影像已经算法处理。
4. 真实成果发布、正式成果文件服务与专业结果查看；没有实际文件不展示伪完成入口。
5. 历史访问申请服务；普通销售本轮彻底移除该入口并拒绝操作，授权账号请求仍返回需正式服务503。
