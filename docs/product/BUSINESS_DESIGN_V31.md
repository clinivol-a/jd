# A方案 V3.1 业务设计边界

分支：feature/a-v3.1-business-design。恢复基线：a-v3.0-review-baseline-20261116（1beeaa6ff126f371550780d6a9918b840e111f5e）。本地设计迭代，不合入交付分支、不部署。

## 当前实现

- 新建订单三选一Dialog，手动沿用原四步；报告与PACS用独立状态流程，同一Order及transition保存/提交。
- 报告仅两张照片；当前适配器不做真实OCR、不读取医院二维码、不向医院下载。明确标示隔离合成资料；识别、授权、获取、核对、失败重试和转人工均可操作。
- PACS连接/检查/序列、患者检查核对为隔离适配器。原始值与人工变更由服务端记录，身份/检查关键字段变化立即失效；不能以修改后值直接声称匹配。
- 患者性别、证件资料仅在勾选医保用途、授权与资料核对后采集；普通订单不强制。订单只存patientIdentityRef、patientSex、insuranceConsent，证件输入不写入浏览器持久状态。当前核对是隔离演示确认，不是正式实名认证。
- 本地业务资料使用AES-256-GCM加密后写入.local/business-v31/records.enc；密钥独立本地文件0600，不入Git/ZIP。正式后端仍需独立密钥管理、字段授权、备份及保留期限。
- 保险汇总按completedAt自然月，使用当前可见订单投影，不使用创建日期。原订单投影未被正式订单/成果接口核验时标记缺项、禁止导出；不采信客户端声称“审核通过/图片批准”。
- 受控导出只接受服务端隔离验收登记的订单、授权账号、手机凭证、完整字段与批准静态图片；记录导出审计。导出一个真正OpenXML .xlsx，包含8字段、文本身份证、日期单元格和嵌入PNG。内部模板，不声称对接医保。
- 本地已授权李明场景具有独立医保导出演示授权；正式版本必须接真实permission及账号原始手机号服务，不从脱敏手机号推断身份。生产构建不安装V3.1测试服务。
- 详情新增成果Card，旧订单未有批准发布的真实资源时保留空状态。独立验收样本不加入原订单/统计/项目或其审核历史；素材为既有CAD原型截图，不是患者正式成果或真实医学计算。
- 一个订单一个有效分享，可撤销。允许的合成医生/患者手机号由服务端样本预授权；OTP成功仍要核对订单allowlist，任意手机号不予访问。访问、拒绝、分享、撤销均有独立审计。
- 分享只提供批准静态展示图；本轮没有真实批准3D成果服务，未伪造3D结果或将原始STL暴露。当前查看器支持静态图平移、缩放；真实只读3D交付/旋转仍待成果服务。
- 销售订单详情取消下载按钮、文件名不再自动下载。图片/PDF按既有权限预览；非可预览医学附件提示进入专业视窗。现有浏览器Blob及原邀请文件接口的完整生产防下载仍未实现：浏览器能显示的内容不能保证无法保存，隐藏按钮/toolbar不是安全边界。正式附件预览需受控渲染服务，禁止源文件直连。

## 新字段

| 字段 | 含义/范围 |
|---|---|
| Order.patientSex | 授权采集性别，普通列表不展示身份证 |
| patientIdentityRef | 加密敏感资料引用，按服务端owner校验 |
| insuranceConsent | 本订单授权医保用途确认；不等于法定签署 |
| insuranceStandard | 后台配置标准id/name/source预留，不硬编码医保目录 |
| importReceipt | 服务端核对引用，按账号/患者/医院/性别匹配复核 |
| importSource | mode/importId/adapter、脱敏original、changes、actor、matched；不混入真实审核 |

## 正式接入及待业务确认

1. 医院OCR与二维码解析、授权影像访问、PACS/DICOM接口及网络策略。
2. 身份/手机号真实短信、患者-订单/医生授权关系，正式隐私同意及审核。
3. 统一订单后端、历史范围权限、实际审核发布的成果登记、受控预览/只读3D派生资源。
4. 正式医保模板、标准项目/编码映射、导出权限授予、敏感数据导出审计及保存期限。
5. 订单完成自动判定仍沿用待确认，不新增“四阶段完成即自动完成”规则。

不改变旧事件、不自动补齐后续审核/成果、不重置任何已有演示账号或工程。

## V3.3 后续定向修订（2026-11-16，优先于上文历史实现）

- 报告/PACS只负责资料获取与核对，之后传入现有OrderEditor四步表单；携带importReceipt、importSource、patientIdentityRef及实际保存的影像/照片附件。手动入口不变，不再维护第二套订单需求表单。业务界面不展示隔离适配器/验收开关，适配器仍是本地合成实现，不声称真实OCR或医院下载。
- resultCatalog.mjs明确登记三个既有合成订单的成果链，不从任意“已完成”状态推导审核通过或发布。订单/项目/任务/成果/版本/图片通过稳定ID关联；不改陈屿工程或生成正式审核日志。其他无成果记录仍不可分享或导出完整资料。
- 医保页读同一关联，证件列表脱敏，服务端核对归属/权限/月度/资料后生成带内嵌PNG的xlsx。当前手术项目名称沿用订单原文，未冒称已完成医保标准目录映射；真实医保目录及患者授权服务仍需正式接入。
- 分享绑定具体resultId/resultVersion/stage，分别校验审核与发布；授权手机号证明才可读取预览。新增只读WebGL预览支持旋转/平移/缩放，采用现有公开演示下颌骨STL的量化显示衍生数据及合成CAD板；每个登记成果有独立ID及对应渲染PNG，不是各患者真实计算结果，不能用于临床或制造。
- 原始STL/CAD不由分享API返回，局域网分享网关禁止源文件路径；浏览器显示衍生几何仍可被技术手段读取，不是DRM。原工程师既有public演示STL未移动或改写；正式环境必须换用授权资源服务。
- 本地业务服务仍只在Vite serve下启用，普通生产构建不包含这些接口；真实短信、医院连接、成果审核/发布及权限服务尚待接入，不能据此直接生产发布。

## V3.5 成果分享记录（2026-11-17）

- 销售阶段卡片保持三行及原高度；记录入口只放在原二维码 Dialog 的复制按钮下方，使用文字操作打开 TDesign Drawer。Drawer 复用 Table、Pagination、Empty，不增加管理员页面。
- 分享按 `shareId/orderId/stageId/resultId/resultVersion` 分隔，发起人来自已登录销售会话，预期接收人来自本订单有权限的需求医生；二者与实际访问者分开。旧分享缺元数据时兼容读取，不追造历史 Viewer 事件。
- 复制链接/图片仅在 Clipboard 成功后提交独立事件，不等同微信发送。页面打开、身份验证与 Viewer 就绪分别记录；服务端以事件 ID 和访问会话 ID 去重。刷新复用当前访问会话，新导航/新标签为新的访问；相同已验证访问者有稳定 ID，可分别计算成功查看和独立访问人数。
- 身份验证通过并不直接计成功；服务端须已交付对应成果资源，前端 Viewer 成功就绪后用绑定该分享/访问会话的证明提交确认。无权限、验证失败、加载失败及重复回调不计成功。撤销、版本、发布与账号范围检查保留。
- 只有手机号授权名单时，只确认手机号持有及该成果访问授权，不把患者姓名或需求医生姓名套给访问者。销售记录显示脱敏手机号及“获授权人员”；有真实可信身份目录映射后才显示姓名、医生/患者等身份。不在记录接口返回原手机号、验证码或访问证明。
- 事件使用既有加密本地业务存储；后续部署适配器可沿既有私有存储持久化，但本轮没有部署、没有改动线上数据。历史审计不删除；原先仅表示验证的旧事件不能回填为确认成功查看。

## 管理员工作台｜后续业务需求

以下全部为**待管理员端设计阶段实施**，仅归档已确认需求，本轮不开发管理员界面或审批接口。

### A. 医生档案管理

1. 医生资质审核通过与退回。
2. 医生资料补充及重新审核。
3. 正式医生档案停用。
4. 已停用医生档案恢复。
5. 医生档案操作审计。
6. 不允许直接硬删除已有正式业务关系的医生。

### B. 销售业务权限管理

1. 医生负责销售归属变更审批。
2. 历史订单访问申请审批。
3. 按区域、医院、科室配置销售管理范围。
4. 普通销售、主管和管理员的授权权限管理。
5. 重要审批操作的审计记录。

### C. 设计成果分享管理

1. 查看管理范围内所有成果分享记录。
2. 按医院、订单、医生、销售、时间筛选。
3. 查看分享发起人和预期分享对象。
4. 查看实际成功访问记录与次数。
5. 识别异常访问。
6. 撤销成果分享权限。
7. 保留成果分享与访问审计。
