# A方案 V3.1 业务设计边界

分支：feature/a-v3.1-business-design。恢复基线：a-v3.0-review-baseline-20261116（1beeaa6ff126f371550780d6a9918b840e111f5e）。本地设计迭代，不合入交付分支、不部署。

## 当前实现

- 新建订单三选一Dialog，手动沿用原四步；报告与PACS用独立状态流程，同一Order及transition保存/提交。
- 报告仅两张照片；当前适配器不做真实OCR、不读取医院二维码、不向医院下载。明确标示隔离合成资料；识别、授权、获取、核对、失败重试和转人工均可操作。
- PACS连接/检查/序列、患者检查核对为隔离适配器。原始值与人工变更由服务端记录，身份/检查关键字段变化立即失效；不能以修改后值直接声称匹配。
- 患者性别、证件资料仅在勾选医保用途、授权与资料核对后采集；普通订单不强制。订单只存patientIdentityRef、patientSex、insuranceConsent，证件输入不写入浏览器持久状态。当前核对是隔离演示确认，不是正式实名认证。
- 本地业务资料使用AES-256-GCM加密后写入.local/business-v31/records.enc；密钥独立本地文件0600，不入Git/ZIP。正式后端仍需独立密钥管理、字段授权、备份及保留期限。
- 保险汇总按completedAt自然月，使用当前可见订单投影，不使用创建日期。原订单投影未被正式订单/成果接口核验时标记缺项、禁止导出；不采信客户端声称“审核通过/图片批准”。
- 受控导出只接受服务端隔离验收登记的订单、授权账号、手机凭证、完整字段与批准静态图片；记录导出审计。导出一个真正OpenXML .xlsx，包含8字段、文本身份证、日期单元格和嵌入PNG。内部模板，不声称对接医保。
- 本地已授权李明场景具有独立医保导出演示授权；正式版本必须接真实permission及账号原始手机号服务，不从脱敏手机号推断身份。生产构建不安装V3.1测试服务。
- 详情新增成果Card，旧订单未有批准发布的真实资源时保留空状态。独立验收样本不加入原订单/统计/项目或其审核历史；素材为既有CAD原型截图，不是患者正式成果或真实医学计算。
- 一个订单一个有效分享，可撤销。允许的合成医生/患者手机号由服务端样本预授权；OTP成功仍要核对订单allowlist，任意手机号不予访问。访问、拒绝、分享、撤销均有独立审计。
- 分享只提供批准静态展示图；本轮没有真实批准3D成果服务，未伪造3D结果或将原始STL暴露。当前查看器支持静态图平移、缩放；真实只读3D交付/旋转仍待成果服务。
- 销售订单详情取消下载按钮、文件名不再自动下载。图片/PDF按既有权限预览；非可预览医学附件提示进入专业视窗。现有浏览器Blob及原邀请文件接口的完整生产防下载仍未实现：浏览器能显示的内容不能保证无法保存，隐藏按钮/toolbar不是安全边界。正式附件预览需受控渲染服务，禁止源文件直连。

## 新字段

| 字段 | 含义/范围 |
|---|---|
| Order.patientSex | 授权采集性别，普通列表不展示身份证 |
| patientIdentityRef | 加密敏感资料引用，按服务端owner校验 |
| insuranceConsent | 本订单授权医保用途确认；不等于法定签署 |
| insuranceStandard | 后台配置标准id/name/source预留，不硬编码医保目录 |
| importReceipt | 服务端核对引用，按账号/患者/医院/性别匹配复核 |
| importSource | mode/importId/adapter、脱敏original、changes、actor、matched；不混入真实审核 |

## 正式接入及待业务确认

1. 医院OCR与二维码解析、授权影像访问、PACS/DICOM接口及网络策略。
2. 身份/手机号真实短信、患者-订单/医生授权关系，正式隐私同意及审核。
3. 统一订单后端、历史范围权限、实际审核发布的成果登记、受控预览/只读3D派生资源。
4. 正式医保模板、标准项目/编码映射、导出权限授予、敏感数据导出审计及保存期限。
5. 订单完成自动判定仍沿用待确认，不新增“四阶段完成即自动完成”规则。

不改变旧事件、不自动补齐后续审核/成果、不重置任何已有演示账号或工程。
