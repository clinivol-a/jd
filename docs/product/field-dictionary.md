# CliniVol A方案｜统一业务字段与状态字典 V1.0

属于《科立沃 A 方案设计与交互规范体系》 / CliniVol A Design System & UX Standards（A方案设计规范）。日期：2026-11-13。本文统一字段语义，不是未经确认的后端数据库或API定稿，不要求为统一文案机械重命名现有属性。

总入口：[AGENTS.md](../../AGENTS.md)；视觉：[tokens.md](../../design-system/tokens.md)；图标：[icons.md](../../design-system/icons.md)；组件与日期格式：[component-rules.md](../../design-system/component-rules.md)；页面组合：[ui-ux-consistency.md](../../design-system/ui-ux-consistency.md)。以当前已确认业务为准，不从旧原型占位内容推导制度。

## 1. 通用显示字段

| 固定名称 | 语义边界 |
|---|---|
| 医院、科室 | 业务所属机构及科室，不用账号单位、自由文本姓名替代稳定关联 |
| 医生 | 执业人员及独立医生档案，不是患者或销售负责人 |
| 患者、患者姓名 | 医疗服务对象与姓名展示；姓名不是去重主键 |
| 病例编号 | Case身份，不等于订单编号或患者姓名 |
| 订单编号 | 销售Order身份，不强制等于工程项目编号 |
| 项目编号、手术项目名称 | 工程Project身份与名称；名称不作关联键 |
| 设计阶段 | 三维重建、CAD设计、有限元分析、3D打印，不再称“专业阶段” |
| 当前进展 | 项目/任务页面规定的进度摘要，不是订单主状态 |
| 订单状态、资质审核状态 | 各自业务状态，不能混为一个status枚举 |
| 最近更新时间、创建时间 | 变更时间与创建时间不同，不能互相补造 |
| 预计交付时间、期望完成时间 | 已确认交付约束与客户申请日期不同，映射见第5章 |
| 操作 | 当前对象、状态与权限允许的动作，不以占位链接冒充能力 |

同义字段跨角色用同名，不同概念不为“统一”合并。例如销售“服务项目”不是工程“设计阶段”；医生资质审核通过不等于订单审核通过。医生手机号按已确认脱敏格式展示，如`199****1003`，操作所需完整值仅在授权场景使用。

## 2. 医生与患者

医生是执业人员；患者是医疗服务对象；病例是具体临床业务记录。医生档案有独立`Doctor.id`及资质状态，电话、姓名、科室只是属性，不可凭姓名关联或合并人员。

病例应通过稳定患者标识与医疗服务对象关联，医生通过`doctorId`关联。当前销售Case模型仅含`patientName?`、`patientRef?`等合成资料，没有因此自动形成真实患者主索引或实名去重。真实患者实体/外部标识接入需另行确认，不在本轮虚构字段或患者资料。

手机号唯一、档案去重和正式销售关联遵守服务端规则；姓名相同不等于同一人，手机验证也不等于完成执业资格或自然人实名认证。

## 3. 病例、订单、项目与专业任务

业务追溯链为 **Case → Order → Project → ProfessionalTask**，是关联层次，不表示当前所有数据已在生产后端实现。

| 实体 | 当前关联/来源 | 约束 |
|---|---|---|
| Case | 销售模型`id`、`doctorId`、可选`hospitalId`/`department`、患者合成标识与临床摘要 | 一个病例可关联多张订单；不因新订单重复造病例 |
| Order | `id`、`caseId`、`doctorId`、`hospitalId`、`department`、`service`、`projectId?`、`taskIds?` | 一单可包含业务服务和多个专业任务；项目尚未实际建立时不虚构projectId |
| Project | 工程项目模型按订单稳定关联聚合，展示项目编号、名称、医院、实际任务集合 | 销售订单号与工程项目号可不同，应凭稳定ID映射追溯 |
| ProfessionalTask | 任务`id`、`orderNo`、`taskType`、状态、所属人、上游任务/成果关联 | 同订单多个任务分别计数；不以任务编号或名称猜阶段依赖 |

当前源码字段见[销售model.ts](../../src/sales/model.ts)、[projectModel.ts](../../src/projects/projectModel.ts)及[App.tsx](../../src/App.tsx)。`orderNo`是既有工程模型关联字段，不能未确认就全部重命名为`orderId`；未来接口应显式映射，避免靠展示编号或字符串拼接连接数据。

共享事件依订单汇总并按唯一事件ID去重；项目详情与专业任务详情有不同可见作用域，不能将“共享数据”理解为每个视图永远展示同一未过滤数组。初始化事件与实际专业执行事件分别识别，保留真实历史，不靠标题/日期/任务编号简单截断。

## 4. 服务项目与设计阶段

服务项目是客户购买或申请的业务服务，例如导板、支具、矫形具、模型；可对应一个或多个专业任务，不等于阶段名称。

设计阶段固定顺序及显示名：

| 顺序 | 显示名 | 既有任务类型兼容 | 专业颜色 |
|---|---|---|---|
| 1 | 三维重建 | 三维重建 | Cyan |
| 2 | CAD设计 | 旧任务模型可能为`CAD 设计`，显示归一，不机械改存量键 | Purple |
| 3 | 有限元分析 | 有限元分析 | Yellow |
| 4 | 3D打印 | 旧任务模型可能为`3D 打印` | Pink |

共用DesignStageIcon/StageLabel，造型、Token、Tooltip和尺寸遵守icons及component-rules。只显示实际配置的阶段，不为了演示四列或丰富时间轴生成不存在任务。阶段卡“等待上游成果审核通过”是当前状态说明，不是已发生流转事件。

## 5. 日期及时间字段

| 标准语义/字段 | 当前模型映射 | 来源与展示 |
|---|---|---|
| `createdAt` 创建时间 | 销售订单`created`；其他模型按既有createdAt或相应创建事件 | 创建时记录，不取首次打开时间 |
| `updatedAt` 最近更新时间 | 订单`updated`；医生`updatedAt?`；工程项目聚合对应实际操作时间 | 不用创建/交付日期冒充最近操作 |
| `requestedDueDate` 期望完成时间 | 同名字段；旧`due`按已有兼容逻辑解释 | 医生与销售提出的目标日期，申请来源可追溯 |
| `confirmedDeliveryDate` 预计交付时间 | 同名字段及已确认订单规则中的有效交付日期 | 已确认的交付约束，不等待三维重建开始才出现 |
| 审核/提交/完成时间 | `reviewedAt?`、`submittedAt?`、`completedAt?`及事件`at`等 | 来自实际发生记录，不由状态展示现场编造 |
| 最后保存时间 | 对应工程持久化成功时间戳 | 不取页面打开/任意点击时间 |

格式只引用[Date & Time Formatting](../../design-system/component-rules.md)与[dateTime.ts](../../src/dateTime.ts)：日期型字段YYYY-MM-DD；近期消息动态显示；审计具体日期时间、跨年补年份；操作与保存采用各自场景函数。需要具体时刻的创建记录属于日期时间场景，不能为了统一日期字段删掉审计时刻。源码局部格式差异见一致性文档冲突登记，本轮不改实现。

现有已确认销售规则：草稿、待审核、审核退回的预计交付可显示“待排期”；处理中、已完成不能缺有效预计交付日期，审核通过时按有效约定交期确认，不以开始专业设计为前提。管理员认为交期不可满足可依审核规则退回；不得新生成“预计实际交付时间已确认”这种额外事件。旧`deliveryConfirmedAt/By`字段保留数据兼容，不等于授权新增操作记录。

## 6. 订单与专业任务状态

### 订单主状态

| 状态 | 含义及边界 |
|---|---|
| 草稿 | 尚未正式提交，可依本人归属、有效关联等条件编辑/删除 |
| 待审核 | 已提交，尚无审核结论，不能提前生成审核通过或完成事件 |
| 审核退回 | 已实际退回，保留对应审核身份、时间和意见 |
| 处理中 | 已审核进入实际执行；有效交期及上下游依赖按现有规则 |
| 已完成 | 只展示已确认发生的完成事实；保留正式成果及审计 |
| 已取消 | 正式取消，区别于删除草稿，不抹除已提交记录 |

不增加“订单待客户确认”等未经确认主状态；已有确认动作或附属字段不能自动上升为新主状态。**订单完成的自动判定条件仍待业务确认**，不得规定“四阶段完成即自动完结订单”。

### 专业任务状态

五种为：未开始、进行中、待审核、审核退回、已完成。对应中性灰、Info蓝、Warning橙、Error红、Success绿；专业色独立于状态色。首页当前进展用这五种简洁状态，项目详情可按现有逻辑显示“CAD设计进行中”，不是新状态枚举。

待处理=进行中+审核退回，是统计分类，不是第六种任务状态。统计任务集与点击列表权限、范围相同，不附加无法查询的历史汇总。

### 审核与审计

审核记录只包含提交审核、审核通过、审核退回等真实审核事件；创建、分配、开始、解锁归流转/活动。保留实际审核人/操作人、任务、成果关联、结果、意见、时间；审核人由授权配置，可以医生、管理员或其他获授权人员，不追改真实历史角色。

流转事件按原始时间倒序、唯一ID去重，不按同名标题去重；不生成未来阶段“等待解锁”、未来审核或完成。上游正式成果审核通过后下游按已确认规则解锁，正式成果只读及唯一关联不变。模拟事件只能属于隔离合成数据，不冒充真实审计日志。

## 7. 医生资质审核状态

四种：**草稿、待审核、审核退回、审核通过**。来自`Doctor.status`，与订单状态及平台登录账号审核状态分别管理；不能因医生填完手机号就认定资质通过。

负责销售归属与正式销售关联受审核及管理员授权规则约束。销售代填记录实际销售操作身份，邀请填写记录邀请Token识别的来源销售和医生本人填写来源；不能允许访问者任改邀请销售。已有档案按服务端去重/关联规则更新或申请，不新建重复档案。

## 8. 我的待办

当前销售待办仅包括四种实际对象来源：

| 事项类型 | 业务对象及原状态 | 分类 |
|---|---|---|
| 订单审核退回 | Order，审核退回 | 需要处理 |
| 订单草稿 | Order，草稿 | 待继续完成 |
| 医生档案审核退回 | Doctor，审核退回 | 需要处理 |
| 医生档案草稿 | Doctor，草稿 | 待继续完成 |

完整页可有“全部”聚合；不包含业务动态，不生成“待处理/未提交/已发送”等第二套对象状态。首页取完整默认待办列表前三条，事项类型展示其真实来源类型，筛选与完整页同口径。字段从实际订单或医生读取，不凭空造“关联对象”替代明确业务字段。点击进入对应对象详情或继续编辑，遵守状态与权限。

## 9. 来源、权限与敏感信息

普通销售仅可按现有规则删除本人未提交且无有效业务关联的草稿；正式提交、审核通过记录不能简单硬删除。正式取消、医生归属变更、停用/恢复、历史订单访问是不同授权行为，详细流程继续按已有销售业务规则，不在字典发明审批制度。

医生/患者姓名、电话、患者标识、病例内容、证件号与附件属于需要保护的信息；按角色、归属、任务/项目授权和业务目的限制访问。列表脱敏不等于接口授权，完整字段和附件下载必须服务端校验。当前隔离账号/本地销售演示逻辑不代表生产权限服务完成。

合成数据必须明确来源并隔离存储，不能用演示映射补造正式医院、审核人或临床结果。销售与工程师共享关联ID，不共享无权查看的数据；账号切换不继承别人的医学视窗或专业Tab。

## 10. 可扩展字段登记

登记至少包括：中文名、代码字段、业务含义、数据来源、显示格式、适用页、敏感性、权限、相似字段区别。以下是当前代码映射，不新增后端实体或强制API命名。

| 中文名 | 当前字段/来源 | 格式与页面 | 敏感性及权限 | 不得混淆 |
|---|---|---|---|---|
| 医院 | `hospitalId`→Hospital.id/name；工程项目hospital | 医院名称；首页/列表/详情/建档 | 业务范围授权；合成目录不宣称合作 | 用户所属单位、患者姓名 |
| 科室 | `department`、Hospital.departments | 目录名称；销售表单/详情 | 跟随机构及业务授权；当前不是独立科室ID模型 | 岗位、设计阶段 |
| 医生 | `doctorId`→Doctor.id/name | 完整姓名；客户/订单/病例 | 个人资料，依归属与授权 | 销售操作人、患者 |
| 联系手机号 | Doctor.phone/手机验证凭证 | 列表脱敏，授权建档输入 | 敏感；服务端验证及查看权限 | 手机号验证≠实名/资质通过 |
| 患者姓名/标识 | Case.patientName?/patientRef? | 授权业务页，缺失不编造 | 敏感临床信息 | 病例编号、医生ID |
| 病例编号 | Case.id；Order.caseId | 当前稳定标识；病例/订单 | 临床访问授权 | 订单/项目编号 |
| 订单编号 | Order.id | 原编号；订单/关联详情 | 订单访问范围 | 工程Project.id |
| 项目编号/名称 | 工程Project.id/name及Order.projectId? | 原项目编号/业务名称 | 项目权限；未创建不造ID | 订单展示号、任务ID |
| 专业任务 | Task.id/orderNo/taskType | 任务编号及阶段；专业工作区 | 所属人、项目及上下游规则 | 手术项目数量 |
| 服务项目 | Order.service | 业务服务名称；销售列表/表单 | 订单访问范围 | 设计阶段 |
| 设计阶段 | plannedStages?/stages/实际Task.taskType | 同一StageLabel；首页/详情 | 跟随项目范围 | 服务项目、任务状态 |
| 当前进展 | 项目实际任务状态投影 | 简洁状态或已确认详情组合文案 | 同统计任务权限 | 订单主状态 |
| 订单状态 | Order.status | 第6章六态 | 操作需对应权限 | 资质/任务status |
| 资质审核状态 | Doctor.status | 第7章四态 | 查看及审核授权分离 | 账号审核状态 |
| 创建时间 | created/createdAt/创建事件 | 第5章日期或明确审计时间场景 | 跟随对象权限 | 最近更新时间 |
| 最近更新时间 | updated/updatedAt/实际最近事件 | dateTime共享函数；最近项目等 | 跟随对象权限 | 创建时间、交付时间 |
| 期望完成时间 | requestedDueDate/旧due兼容 | 日期；申请/订单 | 申请及订单权限 | confirmedDeliveryDate |
| 预计交付时间 | confirmedDeliveryDate/现有交期规则 | 日期；近期订单/详情 | 审核约束及订单权限 | 设计开始时间、实际完成时间 |
| 审核事件 | reviewRecords/审核历史/事件ID及actor、at | 具体审计时间；审核/流转 | 审核授权；身份不可篡改 | 任务分配、计划状态 |
| 附件/证明材料 | Doctor.materials、Order.materials/上传响应 | 文件名、类型、上传状态/预览 | 敏感附件；Token与下载授权 | 本地预览≠服务端上传成功 |
| 操作 | 按对象、状态、当前账号权限计算 | 左对齐操作列/按钮 | 前后端均校验 | 不因UI隐藏即认为安全 |

新字段先确认语义、数据源、隐私与权限，再更新本表；尚未确认的订单完结、真实患者主索引、正式服务接口等保持待确认，不以规范整理强制定稿。

## V3.0 销售订单录入与内容映射（2026-11-13）

- `Order.patientName?`保存本订单手填患者姓名；老订单缺失时从其现有Case读取。姓名只供展示，不作患者去重键。销售新建订单、近期订单/订单表及详情不再展示病例编号或要求选择Case。
- `Order.caseId`继续兼容历史关联。隔离模型保存新单时可建立内部记录；修改患者姓名不覆盖共享Case，不改变其他订单及工程师项目。后台独立Case业务与旧关系没有被删除。
- `Order.clinicalContent?`为version1结构化内容：段落/有序无序列表（text及bold）、图片/视频（已保存Attachment）。`clinicalRequirements`/`requirements`兼容纯文字摘要；不是HTML字段，不能承接任意外部URL。显示以安全结构化内容优先，旧纯文本保持可读。
- 媒体沿用账号owner与稳定文件ID，当前仅浏览器IndexedDB；医学敏感文件不入public，不以临时Blob URL持久化。不代表完成生产跨设备共享或医学附件安全审核。第三步影像要求和订单审核状态机保持不变。

以上更新限定销售订单入口，不要求更改工程师既有病例/患者标识体系。

## V3.1 新业务设计（2026-11-16）

## V3.2 患者与分享规则（2026-11-16，覆盖V3.1可选医保规则）

所有新订单提交必填患者姓名、性别、18位居民身份证，三种录入方式共用患者结构；草稿仍可暂存不完整资料。居民身份证检查格式、出生日期与校验位，不等于联网实名核验；其他证件类型待正式业务目录确认，不按普通非空字符串接受。移除前台医保用途/重复授权核对勾选；实际采集授权、会话与字段权限不因此免除。完整号码仅在受控表单/授权Excel中使用，订单只持久化加密资料引用。
